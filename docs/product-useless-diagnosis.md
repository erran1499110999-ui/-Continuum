# 产品无用根因诊断与价值重构方案（product-useless-diagnosis）

> 编制：researcher（Agent Teams，哲学家视角）｜ 日期：2026-11-07
> 触发：创始人严厉批评「该产品很无用」——本文档把这句话当作**最高优先级的正确判断**来处理：
> 默认创始人对，逐环找「无用」的根因，再给重构方案。不自我安慰、不护短、不把测试数字当挡箭牌。
> 依据：PROGRESS.md 现状、st-plugin-plan.md、failure-case-library.md（23 案例）、research-community.md、
> 企划书第 8 章「最有用的信号是用户是否反复备份、修复、迁移——不是下载量/测试数」。

---

## 1. 激进诊断：为什么现在的产品对用户无用

### 1.1 逐环拆解体验链（每一环都直说）

| 环节 | 现状 | 为什么「无用」 |
|---|---|---|
| **网页版首页** | W1 骨架 + W2 扫描页（PROGRESS.md：目前只有首页+扫描页） | 用户看到的是一个「体检仪」：能查出问题，**开不出药**。备份、恢复、修复全部没有页面。用户带着「我刚误删了聊天」进来，得到一份问题清单然后……没有然后。**查出病开不出药 = 比没有体检更差的体验**（给了希望再抽走） |
| **插件** | 选项 1 规划中（P1–P4 未动工）：内存态 6 项提示 + 唤起 Web UI | 插件「只会提醒不能干活」是设计使然（薄壳原则），但它唤起的是一个**只会扫描的网页**——提醒用户去一个帮不了他的地方。敲门砖敲开的门后是空房间 |
| **核心价值在哪** | 备份/恢复/修复/迁移全在 Python 引擎（364 例测试，已验收） | **价值埋在 CLI 里，目标用户（非开发者）看不到、不会用**。我们引以为傲的引擎，对用户而言约等于不存在。364 例测试证明「代码对」，不证明「产品有用」——这是两件事，此前团队把前者当成了后者 |
| **场景断裂** | 案例库 Top 痛点=白屏抢救（CASE-14）、误删找回（CASE-10）、升级前备份（CASE-13/16） | 产品**没有任何一个入口**对应这三个时刻：没有「酒馆打不开了？点这里救数据」、没有「升级前 5 分钟备份」、没有「从备份找回误删」。用户在出事时刻打开产品，第一眼是通用扫描表单——**场景不存在，产品就等于不存在** |
| **营销与产品两张皮** | marketing-copy 承诺「备份、体检、修复、迁移」四件套；README 首屏三信任点 | 用户按文案下载后只能扫描。文案说的每一条（备份/修复/迁移）在产品界面里都找不到按钮。**承诺与交付的落差本身就是「无用感」的最大来源**——不是产品没有能力，是产品没有把能力交到用户手里 |
| **W 顺序的结构性错误** | W2 扫描 → W3 备份（被暂停）→ W4 恢复 → W5 修复 | 「先诊断、后救治」的工程直觉，在救援类产品里是**反的**：用户是带着事故来的，第一需求是「先保住数据」（备份/急救），其次才是「诊断哪里坏了」。诊断先行、救治后置，等于让溺水的人先填健康问卷 |
| **修复位置错位** | W5 修复预览排得靠前，R0 自动修复项其实很少 | 修复是「有了备份之后才敢做的事」（规则 1/4），且大部分损坏是 R2 仅建议——把修复排在备份/恢复之前，是把最难、最不常用的事放到了最前面 |
| **验证与有用脱节** | 所有验收都是内部（QA 三轮、364 例），真实用户=0 | 没有任何一个真实用户用本产品完成过一次「救数据」动作。**一个从未被用过一次的产品被批「无用」，不是批评，是事实陈述** |
| **「救生员」定位下的能力倒挂** | 企划书定位「数据救生员」 | 救生员的第一个动作是「把人拉上岸」（备份/恢复），但产品第一个可用的动作是「体检报告」。**能力倒挂使定位名存实亡** |

### 1.2 根因一句话

**不是技术不行，是「价值闭环没闭合」：我们交付了引擎，没有交付「用户 10 分钟内能完成的救数据动作」。
产品目前对用户 = 一个只能诊断不能救治的体检仪，且营销把它宣传成了急救包。创始人说「无用」，是准确的。**

## 2. 价值重构方案：最小可用价值闭环（MVP-loop）

### 2.1 定义

> **MVP-loop（构成「有用」的最小闭环）＝ 用户打开产品后，10 分钟内完成一次有意义的救数据动作：**
> **① 一键急救备份**（自动探测酒馆 data 目录 → 单按钮 → 本地生成带 manifest+SHA-256 的完整备份包
> → 显示「备份完成、共 N 文件、可恢复性自检通过」）；
> **② 安全恢复**（从本产品备份包或酒馆内置 backups/ 恢复/找回 → 输出到新目录，绝不覆盖 → 逐文件哈希校验 → 报告）；
> **③ 场景入口**（把①和②挂到用户最痛的两个时刻：**「酒馆打不开/白屏抢救」**与**「升级前 5 分钟备份」**）。
> 体检报告是闭环的第四步（可选、增值），**修复预览与迁移向导是闭环之外的后续**。

### 2.2 功能优先级重排论证（W3/W4 提前、W5 后置）

| 原顺序 | 建议顺序 | 论证 |
|---|---|---|
| W3 备份+校验（已暂停） | **W3' 一键急救备份**（保留原 W3 全部引擎能力，只改 UI 形态：默认目标=自动探测 data 目录，单按钮完成） | 这是「拉上岸」的动作；引擎已具备（manifest/SHA-256 已实现），**UI 工作量最小、价值最大** |
| W4 恢复+回滚 | **W4' 安全恢复/找回**（本产品备份包 + 酒馆 backups/ 两个来源；输出新目录） | 直接命中 Top 1/2 场景（误删找回/白屏抢救）；引擎已有恢复能力 |
| — | **W4.5 场景入口页**（「酒馆打不开？」「升级前体检」两个入口，各 3 步引导） | 把闭环挂到用户到达时刻；纯前端，半天级工作量 |
| W5 修复预览 | **W5' 修复预览（后置）** | 用户手里有了备份才敢让工具动文件；R0 项少、R2 多，价值密度低于备份/恢复 |
| W6–W8 迁移 | 迁移后置到 MVP-loop 验证之后 | 迁移需求真实（CASE-15/16）但非「出事时刻」的刚需；V3/CHARX 缺口尚未闭合 |

### 2.3 插件同步调整（承接「提醒→落地」断裂）

- 插件 P3 唤起按钮从「打开 Web UI 首页」改为**「打开急救备份页（一键备份）或白屏抢救入口」**——
  让敲门砖敲开后有药可取（细节由 developer 在 st-plugin-plan 修订时落实；本文档只定方向）。
- 插件内存态提示（H1–H6）保留，但面板底部主按钮语义必须是「现在去救数据」而非「去了解更多」。

### 2.4 判断标准（闭环是否闭合）

- 一个从未用过命令行的用户，在「误删聊天」状态下：打开 Web UI → 看到「找回误删」入口 → 10 分钟内
  完成找回（输出新目录、可核对）。此流程跑通 = MVP-loop 闭合 = 「有用」成立的第一证据。
- 配套量化：企划书第 8 章「首次成功率 >95%、复用率 >25%」从此闭环开始采集。

## 3. 用户最想解决的 Top 5 场景（基于 23 案例 + 社区调研）

> 满足度 = 当前产品（Web UI W2 现状）对该场景的价值贡献估计，0=完全帮不上。

| # | 场景（案例依据） | 当前满足度 | 缺口 | 补齐成本（估算） |
|---|---|---|---|---|
| 1 | **误删聊天/被重置后找回**（CASE-10「heartbroken」、CASE-01/02/05、#5796） | **5%** | 无 UI 找回入口；引擎恢复能力埋没在 CLI | W4' + 入口页（1–1.5 周） |
| 2 | **酒馆白屏/报错后抢救数据**（CASE-14 NGA、CASE-08 settings 损坏） | **5%** | 无「不依赖酒馆界面」的引导；用户需手工复制 data 文件夹 | W3' 一键急救备份 + 白屏入口（0.5–1 周） |
| 3 | **升级/降级前体检+完整备份**（CASE-13 小酒窝、CASE-16 官方警告、CASE-02） | **15%** | 有扫描无备份；无「升级前」专属入口 | W3'（复用）+ 入口页 |
| 4 | **角色卡导入失败诊断**（CASE-17/18/19、#3560） | **30%** | 扫描可识别损坏卡/纯图片；修复与「正确下载指引」无 UI | W5' 部分 + 提示话术（后置，0.5 周） |
| 5 | **换机/跨版本整包迁移**（CASE-15 GitCode、SillyDroid 需求） | **5%** | 引擎迁移无 UI；V3/CHARX 缺口未闭合 | W6+（后置，视外部会话进度） |

**结论**：前三个场景合计覆盖了 23 案例中情绪强度最高、频率最高的部分，全部由「W3' 一键急救备份 +
W4' 安全恢复 + 场景入口」这一个闭环解决——**补齐成本约 2–2.5 周，却能把产品从「无用」拉到「在
出事时刻有用」**。这正是重构的性价比所在。

## 4. 给 5 人快测问卷新增 3 个问题（让真实用户替我们排序）

> 追加到企划书 12.2 提纲之后；不先推销产品，只问经历与排序。

1. **功能排序题**：「假如只能先做一个，你希望先有哪个？（排序 1–5）A. 一键完整备份（含可恢复性校验）
   B. 误删聊天找回 C. 损坏角色卡诊断与修复建议 D. 升级前体检报告 E. 换机整包迁移」——
   目的：验证第 3 节 Top 5 排序，直接决定 W3'–W5' 的先后。
2. **紧迫性题**：「过去一个月，你是否遇到过误删/白屏/升级后异常/导入失败？当时你花了多久解决、
   用了什么办法？如果有个本地工具能在 10 分钟内帮你，你最希望它第一步做什么？」——
   目的：确认「出事时刻」是否真实高频，以及 10 分钟价值主张是否成立。
3. **价值锚点题**（仅在第 2 题回答「遇到过」的用户上问）：「如果这个工具今天就帮你救回了那一次，
   你愿意为它付多少钱？（0 / 1–10 / 11–40 / 41–100 / 100 元以上）」——
   目的：把 12 章「2 个付费信号」从模糊意愿变成具体锚点；对应场景付费意愿而非泛泛订阅意愿。

## 5. 一句话重定义产品

**旧定位（错误）**：「本地优先的备份、体检、修复与迁移工具」——把四件事平铺，用户不知道先信哪个、
先点哪个，且当下能用的只有体检。

**新定位（建议）**：**「酒馆出事时的本地急救包——10 分钟把你的角色、聊天与设定完整救下来；
体检、修复、迁移是救下来之后的增值。」**

- 配套动作：README/落地页/插件文案按新定位改写（marketing-copy.md 后续修订，本批次仅提方向）；
- 验证门槛不变：conditional-go 四条件 + 本报告 §2.4 的 MVP-loop 闭环测试；
- 若 5 人快测证明「10 分钟急救」也无人需要，则下一层诚实结论是：**连急救都不是需求，产品应收缩为
  免费开源诊断脚本**——该结论同样写在这里，供创始人届时直接取用。
