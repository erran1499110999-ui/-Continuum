# 前端设计流程（创始人 v2026-11-07，权威规范）

> 来源：创始人 2026-11-07 指令（原文存会话记录）。本文件为团队执行规范，优先级高于旧笔记；
> 冲突时以本文件为准。附件截图（浅色）存 .tmp\frontend-brief.png（深色截图待创始人补发）。

## 一、目标与优先级
把当前页面从“设计规范展示页”观感整理成清晰、可信、可继续迭代的产品首页。保留原有功能、暖色气质、浅/深主题与必要内容；重点改进：中文字体、信息层级、页面排布、控件含义、辅助文字可读性、窄屏适配。
优先级：1) 本规范明确要求；2) 项目现有真实功能与架构；3) 旧设计说明中不冲突的内容。
**旧笔记「保留霞鹜文楷」已废弃：中文标题不得使用楷体或手写风格字体。**

## 二、开始修改前
1. 检查项目入口、当前预览页、CSS/JS、主题切换方式与设计说明；确认截图对应页面与文件。
2. 查看 Git 状态，保留已有改动，不覆盖无关文件。
3. 列出拟修改文件；修改前为这些文件保留独立备份/可恢复快照；不复制 .env/密钥/凭据。
4. 先核实现有控件真实行为再改标签与提示；不得因视觉调整改变备份/诊断/修复/路径读取等业务逻辑。

## 三、页面排布
- 桌面：延续单页结构，不凭空增加功能/仪表盘/导航项。顶部主视觉双栏：左产品价值说明、右主要目录操作；按窗口宽度调比例，避免标题挤窄、孤字换行、右侧控件过宽。
- 中文主标题保留原意，调整字号/栏宽/断行，避免“家。”单独掉行；两行长度自然均衡。
- 标题+说明+按钮一组；右侧输入操作单独成组；两组视觉中心对齐、间距有节奏，不用大面积空白造“高级感”。
- 主视觉后出现 R0–R3 说明区：四种状态清楚可比较，但不要每项都做成厚重同等强调大卡片；用统一对齐、留白、浅表面区分。
- 限制正文宽度，复用项目已有布局/间距变量；不为对齐截图写死整页宽高。
- 窄屏：布局不再舒适时切单列（标题说明→目录操作→R0–R3）；主按钮与输入框不得挤压/截断/横向滚动；按钮可换行或纵向排列，主次明确；R0–R3 两列或单列，由可用宽度决定；至少检查 1024/768/390/320px；沿用项目已有断点体系。

## 四、字体与文案
- 中文大标题、章节标题：宋体风格，优先 Noto Serif SC/思源宋体；未 vendoring 则系统回退 `"Songti SC","STSong","SimSun",serif`。
- 中文正文/导航/按钮/标签/说明：黑体风格，优先项目已有字体，回退 `"Noto Sans SC","PingFang SC","Microsoft YaHei",sans-serif`。
- 禁楷体、霞鹜文楷、手写风格；不得用 CSS 字体合成或斜体把宋体变仿手写。
- 不下载/新增未经许可证流程批准的字体；如确需新字体只记录建议与许可证需求，本轮用已批准资源+系统回退。
- 中文标题不照搬西文负字距，保持自然字距；正文行距适合连续阅读。
- 避免中英重复表达；英文只作简短辅助标识或品牌副标题。
- 保留产品真实功能描述；不得新增未经代码/文档证实的隐私、安全、自动修复承诺。

## 五、目录操作区
- 按字段真实行为定文案；“只读输入”不得与可编辑输入混用视觉与提示。
- 路径可编辑 → 清晰标签（如“待检查目录”）+ 说明可输入/粘贴路径；只读 → 明确展示只读状态与数据来源。
- 主操作文字要能看出结果（如“开始检查”）；图标可保留但不得是唯一含义来源。
- 输入框、按钮、提示稳定对齐；验证错误/处理中/完成状态在原有逻辑允许时清晰显示。
- 旧样例里的“composer、focus-within、焦点环、36px 圆形”等实现注释不得混进最终产品文案；预览页保留注释时放独立组件说明区，与真实控件明显区分。

## 六、R0–R3 状态区
- 保留 R0/R1/R2/R3 真实含义与安全规则，不得重新定义等级或改触发逻辑。
- 每级文字+图标双通道表达状态，颜色仅辅助，色弱可区分。
- 统一图标、等级标记、标题、说明对齐；长说明窄屏自然换行。
- 减轻重复卡片感：用标题、间距、细分隔、浅色表面、少量强调色建立层级；不堆浓重边框/阴影/大面积专属底色。

## 七、浅色与深色主题
- 保留两主题总体方向：浅=暖奶油/陶土色；深=森林绿/柔和绿色。
- 优先扩展、整理已有语义令牌；不在每个组件各写一套颜色。
- 至少明确语义角色：背景、主要表面、正文、次要文字、边框、主操作、主操作文字、焦点环、成功/警告/建议/危险状态。
- 两主题同一语义角色保持稳定（主操作始终是主操作，R1 始终表示需确认）；允许配色不同，不得让状态含义随主题改变。
- 截图较淡的占位符、输入说明、次要文字提高可读性；核对对比度并在交付说明列出检查方式；不凭“看起来够亮”判断。
- 阴影与玻璃效果从简：保留识别输入区域的表面差异即可；**不新增粒子、光斑或装饰性动画**。

## 八、交互与无障碍
- 保留现有主题切换与业务事件绑定；改 DOM 不得丢事件/表单提交/键盘操作/自动化选择器依赖。
- 输入、按钮、主题切换保留清晰键盘焦点样式；不移除可见焦点而不给替代。
- 图标按钮必须有可访问名称；装饰图标不重复朗读文字标签。
- 输入报错与动态结果通过语义提示可被辅助技术读取。
- 主要交互状态完整：默认/悬停/按下/键盘聚焦/禁用/加载/成功/错误（只实现项目真实支持的状态）。
- 动效简短且只反馈状态变化；尊重 prefers-reduced-motion；不得加循环背景动画、悬停上浮或无功能动效。
- 触控目标易点；窄屏相邻图标按钮不互相挤压。

## 九、工程约束
- 沿用零构建原生 JS + 纯 CSS（除非检查确认架构已变）。
- 不新增 npm 包、CDN、运行时网络依赖或未批准外部资源。
- 样式优先集中维护的 CSS 自定义属性与语义类名；避免内联样式堆叠、复制主题规则、!important、依赖 DOM 层级的脆弱选择器。
- 复用现有组件/命名/主题切换机制/状态色令牌/交互代码；不因视觉调整重写业务逻辑。
- 纯预览样式与实际产品样式区分清楚；设计注释/预览专属示例/实验控件不得进正式产品页。
- 新增 CSS 变量/组件类/设计规则用可复用、语义明确命名，并在交付说明列出。

## 十、执行与交付顺序
1. 检查项目与现有改动，确认目标文件与架构。
2. 目标文件存可恢复快照。
3. 按规范直接修改页面。
4. 浅/深主题下查看结果；人工检查 1024/768/390/320 宽度布局。
5. 检查控制台错误、资源加载错误、主按钮与主题切换仍按原逻辑工作；不新增测试框架；只运行与本次改动相关的已有验证。
6. 修复发现的问题后再交付。
交付说明必须包含：实际修改文件及职责；中文标题字体如何保证不用楷体及回退策略；两主题语义色彩对应；窄屏与交互状态检查结果；验证方式、已知限制、需后续审批的字体/资源事项。
如截图与代码真实功能不一致，以代码为准并在交付说明指出差异。不覆盖本次以外的用户改动。
