## 1. 产品可行性评估

### 1.1 技术可行性：可行，风险已量化

| 维度 | 现状 | 结论 |
|---|---|---|
| 核心引擎 | 已验收并上 GitHub（扫描/备份恢复/修复预览/迁移，181 passed + 1 skipped 真实运行） | ✅ 底座成立 |
| 格式适配 | V1/V2 已支持；**V3/CHARX/1.12+ 布局是已知缺口**，P0/P1/P2 清单已列（research-sillytavern.md 第 9 节），由外部会话推进 | ⚠️ 有排期、无阻塞 |
| 本地 Web UI | 方案 A（零依赖 ThreadingHTTPServer + 原生 JS）已跑通 W1/W2，端口 8777 | ✅ 路线验证 |
| ST 插件 | 三选项已调研（最小插件→sidecar 完整版→server 插件版），选项 1/2 有直接先例（nat20-bridge） | ✅ 技术可行 |
| 主要长期风险 | ST 迭代快（一年内 1.12→1.19 多次破坏性变更） | 已定策略：核心逻辑留 Python 引擎、插件薄壳、能力检测、每 release 冒烟测试（research-st-plugin.md 第 4 节） |

### 1.2 市场验证现状：需求证据强，但企划书第 12 章正式门槛尚未达成

对照第 12 章 12.3 继续/停止门槛：

| 门槛 | 公开渠道证据 | 状态 |
|---|---|---|
| ≥5/10 人讲述真实迁移/损坏/恢复问题 | 社区调研收集 **15+ 起独立公开案例**（7 个痛点聚类；多条官方确认缺陷；用户原话情感强度高："heartbroken"） | **初步证据强**；但「5/10」为访谈口径，须创始人访谈复证（12.2 提纲已可补充案例库问题） |
| ≥3 人愿提供脱敏样本 | 多位 issue 作者公开过文件，但未授权本项目 | **待授权**（可在社区发布免费诊断器时换取授权样本，见 3.4） |
| ≥3 人愿试用 | 无法从公开渠道观察 | **待访谈/待发布** |
| ≥2 人愿付费/预售 | 未见为「备份/迁移工具」付费的直接公开证据；免费替代品（Cloud Saves、RecordRecoveryAssistant）存在 | **无证据** |

**判定**：痛点真实且被官方 bug 反复印证，产品有存在价值；但按企划书原话「若第 1 周访谈发现用户痛点不强，应该修改定位」——本规划的默认姿态是**先以免费诊断器形态验证，再谈商业化**，不把付费功能开发前置。

### 1.3 风险对照（企划书第 13 章 → 当前缓解）

| 风险 | 缓解现状 |
|---|---|
| 现有免费工具足够、用户不付费 | 差异化证据已收集：ST 内置备份有数周空洞/中文名碰撞/覆盖不保真等**已确认缺陷**（案例库 P0）；把「独立于 ST 界面的外部备份 + 体检」做成增量价值 |
| 客户端格式频繁变化 | 版本化适配器 + 样本回归库（失败案例库第 5 节设计输入）+ 未知字段原样保留（规则 9） |
| 误修导致数据丢失 | 只读扫描、修复副本、diff、R0/R1/R2 分级（已有实现）；案例库 P0 场景直接进回归 |
| 私密聊天泄漏 | 本地优先、不上传（规则 2）；UI 明示「数据不出本机」 |
| 版权/成人内容/未成年人 | 产品只处理用户本地文件、不托管内容——合规面小；分发渠道遵守社区规则（4.4） |
| 市场规模不足 | 企划书既定：以真实活跃用户/重复使用/付费验证为准，不做 TAM 主张（本团队所有报告已遵守） |

## 2. 商业性规划

### 2.1 定位（与营销文档联动，详见 marketing-copy.md）

- **一句话定位候选**：「本地优先的 SillyTavern 数据救生员——备份、体检、修复、迁移，数据不出你的电脑。」
- **三块一体**（创始人指令 4）：引擎（信任基础）→ 本地 Web UI（主界面与付费路径）→ ST 插件（获客敲门砖：酒馆内轻量体检 + 一键打开 Web UI）。**插件不承载深度功能与付费**，全部导向 Web UI。

### 2.2 免费/付费分层建议（承接企划书 4.3，价格为测试假设）

| 层级 | 建议内容 | 建议价格（测试） | 开放时机 |
|---|---|---|---|
| 免费版 | 单角色扫描、基础格式校验、有限备份、报告查看 | ¥0 | 现在（W3 起逐步成型） |
| 个人 Pro（一次性） | 批量备份/体检、修复预览、版本比较、迁移报告、无界面抢救（CLI） | ¥39–99 或 US$8–15 | 出现「重复使用证据」（复用率>25%）后 |
| Creator Pro（订阅） | 角色版本管理、批量发布、兼容性报告、创作者页 | ¥19–49/月 或 US$4–8/月 | V1 阶段（创作者工作台） |
| 团队/工作室（订阅） | 多人协作、私有资料库、审核与批量工作流 | ¥99–299/月起 | V2 阶段 |

**原则**（企划书 4.3 原文精神）：价格只是测试假设；先访谈、落地页、真实付款意愿测试，**不先建支付系统**。

### 2.3 变现路径与时机

1. **现在–第 8 周**：全免费。免费诊断器 + 兼容性报告在社区分发（4.4），换取授权样本、访谈对象与口碑；这是「获客资产」而非收入。
2. **第 9–10 周（可用性测试）**：5–10 名外部用户完成备份→恢复全流程；收集复用率初值。
3. **第 11–12 周（收费验证）**：价格访谈/预售意向测试；若 ≥2 个真实付费/预售信号 → 开放个人 Pro 一次性买断；若不达标 → 维持免费开源诊断器定位，缩小范围（企划书 12.3 的收缩路径）。
4. **MVP1 验收后**：插件选项 2（sidecar 完整版）上线，把「酒馆内一键体检」变成 Web UI 的常态化引流；第二客户端适配器调研启动。

### 2.4 规则 8 合规声明

- 本规划**不含** NFT、代币、钱包、加密货币支付、云端上传功能建议。
- st-saves 式「备份到用户私有 GitHub 仓库」**默认不做**；若未来用户主动要求私有存储备份，须创始人单独裁决且默认关闭、明示风险（对照规则 2 与规则 8 精神）。
- 收入路径全部基于本地软件功能（买断/订阅），与「数据不上传」卖点同向。

### 3.3 并行线与依赖

- **并行**：外部会话（V3/CHARX/1.12+）与 Web UI W3–W8 无写作用域冲突，可同步推进；qa-reviewer 每 W 三轮审核。
- **依赖创始人决策**：① W3 开工令；② UI 风格二选一（见 ui-design-direction.md）；③ ST 插件命名/命令名/版本/许可证默认值；④ GitHub 每阶段推送（已配置）。
- **样本库**：失败案例库第 5 节的合成样本设计 → tests/ 与 samples/synthetic 的规划输入（只建议，实施由对应写作用域成员负责）。

## 4. 结论区：给创始人的决策建议（3–5 条）

1. **立即恢复 W3（备份+校验模块）**，并以失败案例库 P0 场景（备份空洞检测、中文名处理、settings 损坏、integrity 缺失）作为 W3 验收与回归的显式输入；V3/CHARX 更新与 W3 并行、不互相阻塞。
2. **商业化节奏后置**：第 12 章门槛未达前不开发付费功能、不建支付系统；先在社区以「免费诊断器 + 真实案例科普」发布（4.4 策略），目标是拿到 ≥3 个授权样本与 ≥3 个试用者，再谈 Pro。若访谈不达标，按企划书收缩为免费开源诊断器。
3. **UI 风格请二选一**（本团队已备两套方案，推荐「暗色科技风」：目标用户与 ST 使用场景都是暗色深夜环境，且与 Linear 式专业感一致；「明亮极简风」为备选）——详见 ui-design-direction.md，选择后并入 W3 完成（创始人指令 3）。
4. **ST 插件按选项 1 立项**（最小插件：酒馆内轻量体检 + 一键唤起本地 Web UI，1–2 周量级），随第 9–10 周可用性测试发布；选项 2（sidecar 完整版）待 MVP1 验收后再议；选项 3（server 插件）默认不做。
5. **把「独立于 ST 界面也能抢救数据」写入产品核心文案**：案例库显示「酒馆白屏后手工搬 data 文件夹」是中文社区高频求救场景，这正是引擎版（CLI/Web UI）相对插件的不可替代价值——建议 README/落地页首屏即强调。
