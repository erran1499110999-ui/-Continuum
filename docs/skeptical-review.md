## 批次 1（2026-11-07）

### Q1 我们是否在用「质量叙事」掩盖「需求未验证」？
- 【质疑】数百例测试、三轮审核、全注释……工程上是模范生，但市场侧仍是零：授权样本 0、装机 0、
  付费信号 0。团队精力是否过度偏向「把事情做对」而回避「做对的事情」？
- 【证据】AGENTS.md 测试基线 182 collected（最新口径 364）；企划书 12 章四项门槛全部未达成
  （plugin-market-validation §6）；failure-case-library 23 案例全部为公开二手案例。
- 【初步回答】投放冻结（规则 13）已把闸门放下，但「冻结」不等于「验证在推进」——验证需要真人，
  当前团队无任何获得真人的路径（凭据渠道未开、内容页未发）。
- 【建议】把「12 章四项门槛 + 当前数值」写进 PROGRESS.md 置顶区，让创始人每次看板都能看到缺口。
- 【状态】待创始人采纳

### Q2 价格数字是否已在文档间漂移，存在「测试假设被当成事实」的风险？
- 【质疑】企划书明言「不要把价格当成已验证市场事实」，但 marketing-copy 模板、product-plan 分层
  反复出现 ¥39–99 / $8–15 等数字，读文档的人（包括未来的对外文案写手）可能顺手引用成真。
- 【证据】plan-docx-text.txt 第 148 行原话；marketing-copy.md 无价格但 product-plan.md §2.2 含价格表；
  business-feed #1/#2 引用竞品价格。
- 【初步回答】内部文档风险可控，但对外文案必须去价格化，直到第 11–12 周价格访谈完成。
- 【建议】在 marketing-copy.md 合规红线追加一条：「对外文案不出现任何具体价格，直到创始人确认」。
- 【状态】建议中

### Q3 ST 插件「最高优先级」与「市场验证未完成」是否自相矛盾——先造枪再找靶？
- 【质疑】规则 9 把插件定为最高优先级，规则 13 又要求先验证再投放；若真机验证发现双进程/移动端
  问题（质疑 #7/#10），插件 P1–P4 的投入可能部分作废。是否应把「5 人真机内测」前置到 P2 完成时，
  而不是 P4 全部做完才验？
- 【证据】st-plugin-plan.md §4：P3 才有创始人实测，P4 才真实验收；plugin-market-validation §5 Q7/Q10。
- 【初步回答】有矛盾，但可低成本消解：P2（体检模块）完成后即找 3–5 人做「只装插件不装 Web UI」
  的可用性快测，提前暴露安装摩擦与话术误读，再决定 P3/P4 投入节奏。
- 【建议】lead 把「P2 后快测」并入 st-plugin-plan 验收安排（需创始人确认，属 developer 文档）。
- 【状态】待 lead/创始人裁决

### Q4 我们的「案例驱动体检」是不是在为自己的失败案例库做循环论证？
- 【质疑】体检项全部来自我们收集的 23 案例——若样本选择有偏（只收集了能搜到的事故），体检项
  就可能系统性漏掉「没有公开报道的高频事故」（比如安静的字段丢失、不报错的损坏）。
- 【证据】failure-case-library 全部案例来自 GitHub Issues/中文社区公开帖；无真实授权样本对照。
- 【初步回答】承认：公开案例是「下界」而非全貌；补真实样本是唯一解（12 章「3 样本」门槛）。
- 【建议】每接受一个授权样本，回溯检查现有体检项是否漏检，把「案例→检测项」映射表持续更新。
- 【状态】待验证（依赖样本授权）

## 批次 2（2026-11-07）

### Q5 注释全覆盖（规则 11）会不会把「注释审查」变成形式主义，反而稀释关键注释？
- 【质疑】「全部代码补中文注释」若执行成逐行堆砌，会把关键逻辑淹没在噪音里；qa 第 1 轮「注释与
  代码一致性」核查若无标准，会变成「有注释即通过」。
- 【证据】AGENTS.md 规则 6/11；comment-review.md 已存在（外部会话注释审查文档）。
- 【初步回答】需要分级标准：模块 docstring（必）+ 关键分支/魔法值（必）+ 复杂算法意图（必）；
  禁止「x = x + 1 自增」类噪音注释；qa 审查「关键处是否有注释且与代码一致」而非「行数够不够」。
- 【建议】由 qa 起草「注释标准 3 条」经创始人确认后执行。
- 【状态】待采纳

### Q6 语义令牌集中维护会不会成为迭代瓶颈，令牌表膨胀后谁负责裁剪？

  迭代无限膨胀，最终回到「每个组件各写一套」的反面。
- 【证据】frontend-redesign-brief.md §七/九；ui-design-direction.md §3（语义角色清单 12 项）。

- 【建议】frontend 交付说明模板固定「令牌变更：新增 X、废弃 Y」小节。

### Q11 「10 分钟急救」若遇到「本来就没有备份可恢复」，产品是不是又一次承诺了做不到的事？
- 【质疑】误删找回的前提是存在可恢复源（酒馆 backups/ 或本产品备份包）；案例 #5796 证明酒馆内置
  备份有数周空洞——用户在出事时刻第一次打开本产品时，**通常还没有本产品的备份**。此时「急救」
  能给的只是「从今往后的备份」，而不是用户以为的「找回刚才丢的」。若不诚实说明，就是第二次
  「承诺-交付落差」。
- 【证据】failure-case-library CASE-05/#5796；product-useless-diagnosis §2.1 的「找回」表述。
- 【初步回答】急救备份页与找回入口必须分级话术：① 有本产品备份包→恢复；② 有酒馆 backups/→扫描
  找回（标注空洞风险）；③ 什么都没有→明确「这次无法找回，立即建立本产品备份防止下一次」。
  不假装能救已无源的数据（规则 4）。
- 【建议】W4' 恢复页交互按上述三态设计；文案红线进入 marketing-copy 合规清单。
- 【状态】待验证（样本：酒馆 backups/ 真实结构多样性）

## 批次 4（2026-11-07）

### Q12 深链 auto=1「自动开始」是否变相绕开用户确认？
- 【质疑】自动开始对备份类（只读+输出新目录）无害，但若 restore 也带 auto=1，等于一键触发恢复——
  恢复涉及目标目录选择与覆盖边界，必须人工确认。
- 【证据】plugin-viability-plan.md §2/§4 深链机制（#w=emergency&auto=1）。
- 【初步回答】契约应设**深链白名单**：`auto=1` 仅允许 emergency-backup / backup / scan（只读或输出类）；
  restore 深链只跳页面、不自动开始，且目标目录必须用户显式确认（延续规则 1/4）。
- 【建议】developer 实现 P5 时把白名单写进 API 契约与测试（qa 第 2 轮审计点）。
- 【状态】待实现时采纳

### Q13 Image() ping 探测 = 本地服务指纹外泄，接受吗？
- 【质疑】任何网页都可嵌入 `img src=127.0.0.1:8777/api/ping` 探测用户是否装了 Continuity——
  这等于向任意网站泄露「软件指纹」（装了/没装/在跑）。
- 【证据】plugin-viability-plan.md §5 风险表 1/2；Image() 探测为经典零 CORS 技巧。
- 【初步回答】泄露量=「服务是否在跑」这一位信息，无数据无副作用；可接受，但两个硬条件：
  ① ping 响应**不得含版本号等指纹**（仅 `{"status":"ok"}`）；② Host 白名单校验为批准前置。
- 【建议】把这两条写进创始人批准材料（§5 待批 1）。
- 【状态】待创始人批准时采纳

### Q14 「先不管网页端」会不会被误读为「网页端冻结」，导致工作流页无人做？

  P5 与 W3'/W4' API 化联动开发。
